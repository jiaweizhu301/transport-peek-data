TransportPeek — Privacy Policy

Last updated: 2026-10-20

Summary

TransportPeek shows public transport departure times for Sydney. It has no accounts, no sign-in, and no user profiles, and we do not sell personal information. This policy is published by the developer of TransportPeek (“we”). It lists every place data goes when you use the app, including the Google, Cloudflare and GitHub services the app relies on.

What stays on your device

  • Your saved favourites (a stop plus a direction, or a stop-to-stop trip).
  • App settings: language, theme, Wi-Fi-only downloads, refresh interval.
  • The downloaded offline timetable database.

All of the above is stored locally. Favourites and settings may be included in your device's own Android backup if you have that enabled; the timetable database is excluded from backup because it can be re-downloaded.

What leaves your device

  • Real-time requests to our service. When you view a stop or a trip, and when a home-screen widget refreshes, the app asks our service for live departures. The request contains the stop identifiers, the transport mode and, where needed, route and vehicle identifiers, plus a user agent with the app version and Android version. It does not contain your name, an account, your contacts or your location. Our service runs on Cloudflare Workers (see below).
  • Timetable and configuration downloads. The app downloads timetable files and a configuration file from GitHub Releases. GitHub acts as the file host and, as with any download, receives your IP address and the app's user agent.
  • Street map (Google Maps). In versions with a street map, the map is drawn by the Google Maps SDK. When the street map is open, the SDK loads the map tiles for the area on screen from Google's servers, so Google receives your IP address and the map areas you view. See Google's Privacy Policy.
  • Firebase Analytics and Crashlytics (Google) — see “Usage statistics” and “Crash reports”.
  • Google AdMob SDK — see “Advertising”.

Our service keeps short-lived operational data (which stops were recently requested, and a cache of live departures) so it can refresh upstream data efficiently. This data is not linked to a person and is overwritten continuously.

To limit how many requests one connection can make (60 per minute), our service also keeps a per-IP-address request counter. It is held in memory only — it is not written to disk or to a database — and is used only for this rate limit. Each counter covers a 60-second window, but an expired entry is not removed straight away, so your IP address can stay in that memory until the service instance is recycled by Cloudflare.

Cloudflare, which runs our service, also keeps request logs. They can include the request address (which contains the stop and route identifiers), the time, the app's user agent and connection details such as your IP address. These logs are kept for about three days; we use them to monitor and debug the service.

Location

Versions of the app that have “Nearby stops” and the map can use your location. Older test builds without these features do not request location at all.

Location is optional. The app asks for permission when you tap “Find stops near me” or the map's “My location” button, and everything else in the app works without it. Once you have granted permission, the app reads your location while it is open: when the search screen shows nearby stops, when you tap “My location”, and when you open the street map, which then centres on you.

  • Nearby stops: the distance to each stop is worked out on your device from the downloaded timetable. Your location is not part of any request the app sends to our service or to GitHub.
  • Street map: your position is handed to the Google Maps SDK inside the app, which draws it on the map, and the map is centred on it. The SDK then loads the map tiles for that area from Google, so Google can tell roughly which area you are in.
  • The app gets your position from Android's location service. On many phones that service is itself provided by Google, under your phone's location settings.

The app does not save your location to storage, and it is not part of any analytics event or crash report. The app does not request background location permission, and it never tracks where you are over time.

Advertising

The current release shows no ads at all (ads.enabled = false). However, the Google AdMob SDK is bundled and is started when the app launches, so it can contact Google and read the advertising ID even though no ad is displayed. The AdMob SDK will be removed in the next version of the app; this page will be updated then.

Advertising ID

The app's merged manifest includes com.google.android.gms.permission.AD_ID and android.permission.ACCESS_ADSERVICES_AD_ID, brought in by the AdMob SDK. The advertising ID is a resettable device identifier. It is not your name or an account, but it is not anonymous either — so this page does not describe our data as "anonymous"; it says only that data is not linked to your name or to an account.

Usage statistics

The app itself logs five Firebase Analytics events:

  • app_session_start — a foreground session begins (parameter: how it was opened).
  • app_session_end — that session ends (parameter: its length in seconds).
  • stop_detail_open — a departure detail screen was opened.
  • widget_bound — a home-screen widget was linked to a favourite (parameter: its size).
  • widget_bg_refresh — a background widget refresh ran (parameters: whether the screen was on, and whether a network request was made).

These events carry no stop names, no favourites, no search terms and no location. Firebase Analytics also records its own standard events (such as first open and app updates), an app-instance identifier, device model, OS and app version, and a coarse location (such as country and city) that Google works out from your IP address. It also collects the advertising ID by default (see above).

Crash reports

Firebase Crashlytics collects crash stack traces plus device model, OS version, app version, session timing and an installation identifier. It does not collect your favourites or anything you searched for.

Keeping and deleting data

  • On your device: kept until you delete it. Uninstalling the app, or clearing its storage, removes your favourites, settings and timetables (copies in your own Android backup follow your backup settings).
  • Our service: operational data is overwritten continuously; the in-memory rate-limit counters disappear when the service instance is recycled; Cloudflare's request logs are kept for about three days.
  • Google and GitHub keep what they receive under their own policies: Google Privacy Policy, GitHub Privacy Statement.

Because there are no accounts, we cannot look up data by person. Questions are welcome at the contact below.

Security

Every network connection the app makes uses HTTPS (encrypted). The release build does not allow unencrypted HTTP.

Children

The app is not directed at children and does not knowingly collect data from them.

Data sources

Timetable and real-time data come from Transport for NSW under CC BY 4.0. See the attribution page.

Contact

TransportPeek — 隐私政策

最后更新：2026-10-20

一句话

TransportPeek 显示悉尼公共交通的发车时间。没有账号、不需要登录、不建用户画像， 也不出售个人信息。本政策由 TransportPeek 的开发者（下称「我们」）发布， 列出使用 app 时数据会去的每一个地方，包括 app 依赖的 Google、Cloudflare 与 GitHub 服务。

只留在你手机上的

  • 你的收藏（站 + 方向，或者站 A → 站 B）。
  • 应用设置：语言、主题、仅 Wi-Fi 下载、刷新间隔。
  • 下载下来的离线时刻表数据库。

以上全部存在本机。收藏与设置可能会进入安卓自带的备份（如果你开了备份）； 时刻表数据库不进备份，因为它随时可以重新下载。

会离开你手机的

  • 向我们的服务查实时。你打开某个站或某趟车时、以及桌面小组件刷新时， 应用会向我们的服务请求实时发车。请求里有站点标识、交通模式，需要时还有线路与车辆标识， 以及带 app 版本和安卓版本的 User-Agent；不含姓名、账号、通讯录或你的位置。 我们的服务跑在 Cloudflare Workers 上（见下文）。
  • 时刻表与配置下载。应用从 GitHub Releases 下载时刻表文件与配置文件。 GitHub 作为文件托管方，和任何下载一样，会收到你的 IP 地址和 app 的 User-Agent。
  • 街道地图（Google 地图）。带街道地图的版本里，地图由 Google Maps SDK 绘制。 街道地图打开时，SDK 会从 Google 的服务器加载屏幕上那片区域的地图瓦片， 因此 Google 会收到你的 IP 地址和你看过的地图区域，见 Google 隐私权政策。
  • Firebase Analytics 与 Crashlytics（Google）——见「使用统计」「崩溃报告」。
  • Google AdMob SDK——见「广告」。

我们的服务会保留很短期的运行数据（最近被请求过哪些站、实时发车的缓存）， 用于高效刷新上游数据。这些数据不与任何个人关联，并会被持续覆盖。

为了限制单个连接的请求量（每分钟 60 次），我们的服务还会按 IP 地址记一个请求计数。 它只放在内存里，不写进磁盘或数据库，只用于限流。每个计数管 60 秒， 但过期的条目不会立刻清掉，所以你的 IP 地址可能一直留在这块内存里，直到 Cloudflare 回收这个服务实例。

运行我们服务的 Cloudflare 还会保留请求日志，内容可能包括请求地址（里面有站点与线路标识）、时间、 app 的 User-Agent，以及你的 IP 地址等连接信息。这些日志保留约三天，我们用它来监控和排查服务问题。

定位

带「附近站」和地图的 app 版本可以使用你的位置；没有这两个功能的早期测试版完全不申请定位。

定位是可选的。你点「用定位找附近的站」或地图上的「我的位置」按钮时，app 会请求权限； app 的其他功能不需要它也能正常用。授权之后，app 在打开期间会读取你的位置： 搜索页显示附近的站时、你点「我的位置」时，以及你打开街道地图时（地图随即以你为中心）。

  • 附近站：每个站离你多远，是在手机上用下载好的时刻表算出来的。 app 发给我们的服务或 GitHub 的请求里都没有你的位置。
  • 街道地图：你的位置会交给 app 内的 Google Maps SDK，由它画在地图上， 地图也会以它为中心。SDK 随后从 Google 加载那片区域的地图瓦片， 所以 Google 能大致知道你在哪一带。
  • app 通过安卓系统的定位服务取得位置。在很多手机上，这项系统服务本身由 Google 提供， 受你手机定位设置的约束。

app 不把你的位置存进手机存储，位置也不出现在任何统计事件或崩溃报告里。 应用不申请后台定位权限，也不会持续记录你的行踪。

广告

当前版本一个广告都不展示（ads.enabled = false）。 但 Google AdMob SDK 随 app 一起打包，并在启动时初始化，因此即使不展示广告， 它也可能连接 Google 并读取广告 ID。下一个版本会移除 AdMob SDK，届时更新本页。

广告 ID

合并后的权限清单里有 com.google.android.gms.permission.AD_ID 与 android.permission.ACCESS_ADSERVICES_AD_ID，由 AdMob SDK 带入。 广告 ID 是可重置的设备标识符，不是姓名也不是账号，但它也不等于「匿名」—— 所以本页不再使用「匿名」这个说法，只说这些数据不与你的姓名或账号关联。

使用统计

app 自己上报以下 5 个 Firebase Analytics 事件：

  • app_session_start —— 一次前台会话开始（参数：从哪里打开的）。
  • app_session_end —— 这次会话结束（参数：时长秒数）。
  • stop_detail_open —— 打开了某个发车详情页。
  • widget_bound —— 桌面小组件绑定到某条收藏（参数：尺寸）。
  • widget_bg_refresh —— 后台刷新跑了一次（参数：当时是否亮屏、这次有没有发请求）。

这些事件不含站名、不含收藏内容、不含搜索词、不含位置。 Firebase Analytics 还会记录它自带的标准事件（如首次打开、app 更新）、一个 app 实例标识、 机型、系统与 app 版本，以及 Google 根据你的 IP 地址推算出的粗略位置（如国家、城市）。 另外它默认会采集广告 ID（见上一节）。

崩溃报告

Firebase Crashlytics 采集崩溃堆栈，以及机型、系统版本、app 版本、会话时间与一个安装标识。 它不采集你的收藏，也不采集你搜索过什么。

数据保留与删除

  • 手机上：保留到你删除为止。卸载 app 或清除它的存储，会删掉收藏、设置与时刻表 （安卓备份里的副本按你的备份设置处理）。
  • 我们的服务：运行数据持续覆盖；内存里的限流计数随服务实例回收而消失；Cloudflare 的请求日志保留约三天。
  • Google 与 GitHub 按各自的政策保留它们收到的数据： Google 隐私权政策、 GitHub 隐私声明。

因为没有账号，我们无法按人查找数据。有疑问欢迎通过下方联系方式问我们。

安全

app 的所有网络连接都走 HTTPS（加密）。正式版不允许未加密的 HTTP。

儿童

本应用不面向儿童，也不会有意收集儿童数据。

数据来源

时刻表与实时数据来自 Transport for NSW，按 CC BY 4.0 授权使用， 见归属页。
